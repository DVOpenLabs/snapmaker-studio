# Snapmaker Studio — user guide

A static, task-oriented guide for **Snapmaker Studio v1.5.0**. It is organized around the decisions a person makes before a
print, not around the order of the app's menus:

1. **Learn with an example project** — six stages (Open → Check → Prepare → Review → Slice in Orca → Check the sliced job),
   each answering one question with a real screenshot, what the result means, what to do and how to know you are done.
2. **Find help for my current task** — 27 short task pages grouped by need; optional tools are marked optional.
3. **Understand a warning or problem** — 23 pages, one per message Studio shows, each marked by how sure Studio is
   (confirmed, worth checking, unknown, looks right, good to know) and what *not* to conclude.

Four small examples (placement, assigning a material vs loading it, reading a preparation change, unknown vs confirmed
incompatibility) make the reader decide something and explain every answer. They only move between pictures and text.
A workflow map shows which part of the job happens in Studio, in Snapmaker Orca and at the printer. Search covers every
task and warning. The guide needs no backend, no account, no Tauri and no printer, and it runs from any static host.

> Snapmaker Studio is an independent open-source project — not affiliated with or endorsed by Snapmaker.

**Live guide: <https://dvopenlabs.github.io/snapmaker-studio/>** (published by GitHub Pages from `main` whenever `site/guide/` changes).

## What is in this folder

```
site/guide/
  public/                  ← the website. This folder is what you deploy.
    index.html             ← GENERATED by tools/build.mjs (committed, so reviewers can open it)
    assets/guide.css       ← styles (brand tokens, light/dark themes, workflow map, certainty badges)
    assets/guide.js        ← entry: hash router (incl. old lesson links), theme, filters, "continue the example"
    assets/search.js       ← client-side search over the embedded index (excerpts, empty state)
    assets/examples.js     ← the four interactive examples (choose / sort / select-all-that-apply)
    assets/figures.js      ← screenshot viewer and the optional numbered notes on controls
    assets/common.js       ← shared helpers (no network access anywhere)
    assets/theme-init.js   ← applies the saved theme before first paint
    assets/md.js           ← tiny inline-markup renderer shared by the build and the page
    assets/img/            ← screenshots (captured from the real app) — see "Screenshots"
    assets/brand/          ← the approved Studio mark and favicon, copied from docs/brand
  content/
    guide.json             ← site text, links, certainty scale, workflow map, home page, old-link redirects
    path.json              ← the six stages of the example path
    tasks.json             ← task pages (steps, success signal, "if it looks different")
    problems.json          ← warning pages
    examples.json          ← the interactive examples and their feedback
    shots.json             ← each screenshot's alt text, caption and control explanations
    geometry.json          ← GENERATED: where each control sits, as percentages of the picture
    answers.json           ← frozen seven-question manifest for code-backed golden answers
  tools/                   ← build, preview, capture and verification scripts (Node, no runtime dependencies)
  deploy/                  ← sample deployment files (nothing here runs automatically)
  evidence/redesign/       ← screenshots of the finished redesign (desktop and phone, both themes)
  EVIDENCE.md              ← which verified screen or source backs each documented workflow
```

The page is complete HTML without JavaScript (every page is readable, examples appear as worked text, old lesson links
land on the right page). With JavaScript the guide shows one page at a time and adds search, filters and the examples.

## Preview and build

Requires Node 18 or newer. No packages are needed to build or preview.

Stages, tasks and warnings may include a checked version and repository-backed sources. The build validates source paths,
link keys and the shape of the seven golden answers; it checks only the shape and file existence of each `derive`
reference, and the real symbol resolution happens in the tests. Each source appears in a collapsed **Where this comes from** block. The offline
check compares the guide version with the desktop configuration and warns on drift without failing.

```bash
cd site/guide
node tools/build.mjs        # validate content and regenerate public/index.html (fails on any problem)
node tools/serve.mjs        # preview at http://127.0.0.1:4173/  (Ctrl+C to stop)
```

`node tools/build.mjs` refuses to build if a stage, task or warning is missing a field, a link points at a page that does
not exist, an example has no single best answer, a screenshot or its alt text is missing, a control has no captured
position, two controls overlap, or the text contains something that looks like an IP address, a local path, an internal
tool name or a guarantee claim.

## Checks

```bash
node tools/check.mjs        # static checks: links, ids, alt text, no third-party requests, strict-CSP readiness, color contrast
node tools/check.mjs --online   # also confirms that every external link responds
node tools/e2e.mjs          # browser checks (needs Microsoft Edge or Chrome and `playwright-core`)
node tools/e2e.mjs --shots ../../some/folder    # also saves screenshots of the finished guide
node tools/e2e.mjs --url https://example.org/guide/   # test a deployed copy
```

`tools/e2e.mjs` serves `public/` with a strict Content-Security-Policy and, at desktop (1280 px) and phone (390 px)
widths in both themes, opens every page by deep link and every old lesson link, then exercises search (results, excerpts,
empty state, suggestions, the `/` shortcut), task and warning filters, all four examples (including a wrong answer),
the screenshot viewer (focus in, Escape out, focus restored), the optional numbered notes, keyboard-only paths, the theme
switch, a wide fallback font, missing images, horizontal overflow and console errors. A separate no-JavaScript run
checks that every page is readable and every old link has an anchor. If `playwright-core` is not installed here, the
script falls back to the copy in `tools/acceptance/`; otherwise run `npm install` in this folder.

## Deploy

`public/` is plain files with relative URLs, so it works at the root of a domain or in a sub-folder. There is no build
step on the server; commit the regenerated `public/index.html` and publish `public/`.

* **GitHub Pages (how this repository publishes it)** — `.github/workflows/guide-pages.yml` publishes `site/guide/public` on every push to `main`
  that touches `site/guide/`, after `guide-ci.yml` has built, checked and click-tested it on the pull request. Pages is set to
  *Source: GitHub Actions*. `deploy/github-pages.yml.example` is the same workflow, kept for people who fork the guide.
* **Netlify / Cloudflare Pages / any static host** — publish directory `site/guide/public`; no build command is needed (or
  use `node site/guide/tools/build.mjs`).
* **Recommended headers**: `deploy/security-headers.txt` (a strict Content-Security-Policy that the guide is tested under,
  plus the usual hardening headers). The guide loads no third-party script, font, image or stylesheet.

The link used inside Studio's **Help** and **Get Started** pages lives in one place: `desktop/src/lib/guide.ts` (`USER_GUIDE_URL`),
currently `https://dvopenlabs.github.io/snapmaker-studio/`. Change it if the guide is hosted elsewhere.

## Maintain it

* **Change wording** — edit the matching file in `content/` (a stage in `path.json`, a task in `tasks.json`, a warning in
  `problems.json`), and run `node tools/build.mjs`. Inline markup: `**UI label**` (always the exact label shown in Studio),
  `` `code` ``, `*emphasis*`, `[text](https://…)` or `[text](@key)` where `key` is in `links`.
* **Add a task or warning** — add an object with the required fields; the build lists what is missing. Search, the task
  list and the warning list pick it up automatically.
* **Add an example** — add it to `content/examples.json` and name it in a stage's `examples`. Only add one when each
  option and each piece of feedback can be traced to real Studio behavior (record it in `EVIDENCE.md`).
* **Keep old links working** — when a page id changes, add the old id to `redirects` in `content/guide.json`.
* **Change a control's explanation** — edit its `text` in `content/shots.json`, rebuild. Numbers are the order in that list.
* **Add or move a hotspot, or refresh a screenshot** — edit `tools/spec.mjs` and run the capture below.
* **New Studio release** — update `site.version` and the wording, recapture, run the checks, and walk the guide against the
  new build. Hashes and installer names are never copied into the guide: it links to `docs/RELEASE_METADATA.md`.

### Screenshots

Every screenshot is captured from the real Studio interface, with example files from `/examples` and `tools/fixtures.py`.

```bash
node tools/capture.mjs                  # all dev-UI screenshots (starts a disposable engine, the Studio web UI and a
                                        # made-up Spoolman on 127.0.0.1:7912; needs Python, Node, Edge/Chrome)
node tools/capture.mjs --only home,fidelity
pwsh -File tools/capture-installed.ps1 -Installer <release .exe> -Sha <sha256> -SourceVersion 1.5.0
                                        # the screenshots that need the INSTALLED app (handoff.png), inside the
                                        # repository's isolated test harness; never presses "Open in Snapmaker Orca"
```

The capture scripts never connect to a printer, a slicer or the internet; they stop every process they start. Before each
screenshot they replace any local path with `<folder>`. Each run rewrites `content/geometry.json` for the shots it
captured, so hotspots stay aligned. Review new screenshots for private data before committing (this guide's captures use
only synthetic example files and made-up spools).

Evidence kinds use `file` for values read from a file, `engine` for a Studio check, `estimate` for a derived estimate, and
`orca` only for advice to verify in Snapmaker Orca. The last kind makes no claim about Orca behavior.

Studio's own window is captured in its dark theme. The guide itself has both themes. Screenshots of the finished guide are in `evidence/redesign/`.
